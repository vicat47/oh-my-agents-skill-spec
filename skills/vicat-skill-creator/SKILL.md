# vicat-skill-creator

**输入**：用户希望复用的真实请求、目标项目或已有 skill。**产出**：可交接的 skill 包、可复现的验收用例和验证结果。本 Harness 不要求特定包管理器或全局配置。

1. **判断要不要做。** 先看目标项目的约定和已有 skill，再复述用户要解决的一件事。如果已有 skill 适用，优先改进它；若只有“做一个通用助手”之类的描述，先索取一个具体请求，不凭空定义范围。
2. **先写验收，再制作。** 用[验收卡](assets/acceptance.md)填一项真实请求、一个相似但范围外的请求、一个输入或环境错误。写出可观察的结果和不得发生的副作用。卡片可以留在对话中，也可作为包的测试材料。
3. **约定配置与运行行为。** 列清目标如何定位、允许的动作、必需输入、输出、失败和重试。需要配置时，读项目的单一 TOML、复用领域字段，给专属字段附上 JSON Schema 和最小样例。涉及外部系统时核对实例和会话，不能用环境名放宽操作权限。声明哪些运行文件可删；只读且不落盘就直接写明。
4. **制作最小包。** 在项目认可的源目录创建 `<name>/SKILL.md`。frontmatter 填写与目录一致的 `name` 和面向使用者的 `description`。正文从“何时用”通到“如何做、何时停”；确定性操作才提取脚本，详细知识按需引用。用包内相对路径，项目输入独立定位。
5. **分开验收选择和执行。** 从不同于包目录的工作目录运行用例。再把原始请求、可发现的 skill 和项目输入交给未参与开发的 Agent，不给预期答案。选错 → 改触发描述；选对但结果错 → 改契约或实现；换目录就失败 → 改资源定位。修改后重跑受影响的用例。无法做独立交接时明确标记待验证。
6. **交付并留下维护入口。** 报告包位置、依赖、最短运行方式、哪些检查通过、哪些待验证。升级时把现场失败变成回归用例；移除或替代 skill 时说明如何保留用户配置和正式输出。
